# CampusPulse — Neobrutalism Svelte reference analysis and phased redesign

## 1. Reference and research scope

Reference: https://neobrutalism-svelte.flenze.com/

Public source repository: https://github.com/olegpolin/neobrutalism-svelte

The component implementation and setup instructions were audited in the upstream repository: its README, registry manifest, installation and theming documentation, component documentation, Svelte component source, and global stylesheet. This provides a verifiable view of the actual tokens, APIs, dependencies and install procedure rather than inferring them from screenshots alone.

### What the reference project is

- A Svelte 5 component library built on shadcn-svelte.
- Components are shipped as source through a shadcn-svelte registry.
- Its registry manifest lists 34 entries: accordion, avatar, badge, button, button-group, card, checkbox, command, dialog, dropdown-menu, empty, field, input, input-group, item, label, navigation-menu, popover, progress, radio-group, scroll-area, select, separator, sheet, sidebar, skeleton, slider, sonner, spinner, switch, tabs, textarea, tooltip and the is-mobile utility.
- Dropdown menus use Bits UI primitives. The source imports icons from @lucide/svelte.
- The visual system is driven by CSS variables and Tailwind CSS v4. Components are small composable primitives, not a single monolithic theme stylesheet.

## 2. Upstream installation guide — what it means

The source guide targets a new SvelteKit project with Tailwind CSS v4. Its documented sequence is:

1. Create a SvelteKit project and select the Tailwind CSS add-on: npx sv create my-app.
2. Initialize shadcn-svelte: npx shadcn-svelte@latest init.
3. Copy the :root, .dark and @theme inline blocks from the reference theme stylesheet into the target app's global stylesheet, replacing the corresponding blocks generated by the initializer. Keep the other stylesheet imports, custom variant and base layer.
4. Install the variable fonts: npm install @fontsource-variable/dm-sans @fontsource-variable/geist-mono.
5. Import the fonts in the global stylesheet:
   - @import '@fontsource-variable/dm-sans';
   - @import '@fontsource-variable/geist-mono';
6. Add an individual component from the registry, for example:
   npx shadcn-svelte@latest add https://neobrutalism-svelte.flenze.com/r/button.json

Each component's documentation contains its own registry add command. The CLI installs extra packages required by a component, such as Bits UI.

### Compatibility decision for CampusPulse

CampusPulse is a Next.js App Router / React project. The reference registry serves Svelte components and expects Svelte/shadcn-svelte conventions. Its CLI and .svelte files are not drop-in React components. Running the Svelte installer in CampusPulse would add the wrong framework layer and create incompatible source files.

This redesign therefore ports the design principles and component behavior into React-native components. It does not run the Svelte CLI or paste Svelte source into the Next.js project. Existing application data, routes, API endpoints, storage and eligibility logic remain the behavior source while screens are migrated one feature at a time.

## 3. Design system extracted from source

The source stylesheet defines a warm, low-glare neutral canvas, near-black foreground and border, amber primary, muted blue secondary, orange accent, and muted neutral surfaces. The key source values are:

- Background: oklch(0.95 0.02 85).
- Foreground: neutral 950.
- Primary: amber 400.
- Secondary: blue 200.
- Accent: orange 200.
- Muted surface: oklch(0.9 0.02 85).
- Destructive: red 600.
- Border: neutral 900.
- Base radius token: 1rem.
- Base border width: 2px.
- Hard shadow width: 4px, with no blur; smaller and larger shadows are multiples of that width.

The source supports light and dark token sets. CampusPulse's current redesign phase intentionally uses the light theme; a dark-mode experience is not being introduced as part of this first slice.

### Typography

The reference imports:
- DM Sans Variable for body, labels and interface text.
- Geist Mono Variable for code and compact metadata.

There is no separate decorative display font in the reference stylesheet. The CampusPulse adaptation uses heavier DM Sans weights and close tracking for display hierarchy, with Geist Mono for indices, labels and metadata.

### Component anatomy and behavior

The upstream registry uses small composable components. Its Button includes default, destructive, outline, secondary, ghost and link variants, with default, small, large and icon sizes. Button Group supports horizontal and vertical orientation, nested groups, separators, inputs, selects and dropdown split actions. Adjacent buttons share their borders and corner treatment rather than becoming unrelated floating controls.

The Button Group documentation requires a semantic group role and an accessible label using aria-label or aria-labelledby. The dropdown menu supports grouped menu items, radio groups and nested submenus. CampusPulse should preserve those semantic patterns and keyboard access when building the React equivalents.

## 4. Icon and motion decisions

### Icons

The reference uses Lucide. CampusPulse already has lucide-react installed, so the redesign standardizes on the same Lucide outline family instead of adding a second icon set.

Rules:
- Import named icons directly so unused icons can be tree-shaken.
- Use consistent 16–24px sizing and a roughly 2px stroke for normal UI icons.
- Choose icons for the action or feature meaning; do not use emoji as primary navigation/action symbols.
- Every icon-only control must have an accessible name.
- Initial semantic mapping: GraduationCap for scholarships, ListChecks for eligibility, FileSearch for document review, CalendarCheck for follow-ups, Bookmark for saved schemes, ShieldCheck for verification/help, BriefcaseBusiness for services, and UserRound for profile.

References:
- Lucide React: https://lucide.dev/guide/react/
- Lucide stroke width: https://lucide.dev/guide/react/basics/stroke-width

### Motion

CampusPulse already includes Framer Motion. Motion should support hierarchy and comprehension rather than add constant movement.

The homepage phase uses:
- A short staggered entrance for the headline, supporting copy and actions.
- A single, restrained entrance for the product preview.
- Once-only scroll reveals for feature and process sections.
- Small hover/press responses for interactive cards and buttons.
- Reduced-motion support through MotionConfig and a CSS prefers-reduced-motion rule.

Avoid autoplay media, constant parallax, cursor-following decoration and perpetual animations. Preserve readable content and functionality when motion is reduced.

References:
- Reduced motion: https://motion.dev/docs/react-use-reduced-motion
- Accessibility: https://motion.dev/docs/react-accessibility
- In-view reveal: https://motion.dev/docs/react-use-in-view

## 5. Responsive design rules

Treat the available viewport width as the design constraint, including split-screen and narrow desktop windows. The redesign uses bounded content widths, clamp-based typography and spacing, minmax(0, 1fr) grids, wrapping action rows and explicit layout changes at breakpoints.

Do not rely on fixed viewport-height sections, fixed-width cards or absolute positioning for essential content. At narrow widths, change hierarchy and stack content rather than scaling a desktop composition down. Keep keyboard focus visible and touch targets practical. Short landscape windows must remain scrollable and must not hide important content.

Target QA widths: 320px, 360px, 375px, 430px, 520px, 700px, 768px, 850px, 1024px, 1280px and 1440px, with additional narrow split-screen checks.

## 6. CampusPulse phased implementation plan

| Phase | Scope | Exit criteria |
|---|---|---|
| 0 — Research and architecture | Audit upstream components, setup, typography, icons, motion, CampusPulse routes and data flows | Document source facts, compatibility choice and migration order |
| 1 — Public foundation | Design tokens, fonts, responsive landing page, responsive header, icon conventions, motion and entry links | Homepage builds; desktop, split and mobile layouts are checked |
| 2 — App shell and dashboard | New shared app navigation, mobile navigation, page frame and dashboard overview | Existing app routes use one consistent new shell; dashboard data and reminders remain functional |
| 3 — Scholarships | Directory, search, filters, scheme cards, details and official-source links | Search/filter/detail behavior and source caveats remain intact |
| 4 — Student setup and eligibility | Get-started, profile and eligibility checker | Existing profile fields and matching rules remain intact |
| 5 — Personal organization | Saved tracker, statuses, planner and reminders | Local persistence and cross-screen updates remain intact |
| 6 — Student support tools | Services, document review and rejection analyzer | Existing API calls, validation and privacy safeguards remain intact |
| 7 — Quality pass | Responsive QA across routes, keyboard and assistive-technology checks, loading/empty/error states, performance and visual consistency | No critical layout overflow or broken core workflow remains |

Each phase should be implemented and checked as a vertical slice. Do not combine unrelated business-logic changes with a visual migration.

## 7. Phase 1 implementation status

Phase 1 is isolated in the new components/redesign namespace and app/redesign.css. The root route now serves the new public homepage instead of redirecting directly to the dashboard. The existing AppShell deliberately bypasses its prior shell at the root route; other routes retain their current shell until the next phase.

The first slice includes:
- DM Sans and Geist Mono font loading through Next.js font support.
- A namespaced warm-neutral / amber / blue / orange token layer.
- A responsive public header with a mobile navigation menu.
- A purpose-built HTML/Lucide workspace preview, not a static screenshot.
- Six feature links into existing CampusPulse capabilities.
- A simple three-step explanation and a final call to action.
- Staggered entrance and in-view motion with reduced-motion handling.

This is not a claim that the whole application has been redesigned. The existing dashboard and feature screens are intentionally scheduled for subsequent phases. Browser visual QA and full route QA are separate gates and must be completed before calling the overall redesign finished.
